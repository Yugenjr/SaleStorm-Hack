# Payment Database Design

The payment design ensures exact, safe handling of transactions and prevents duplicate charges in the event of retries or network timeouts.

## PAYMENT Table

| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `payment_id` | UUID | PK | Internal unique identifier for the payment attempt. |
| `order_id` | UUID | FK, INDEX | Link to the respective order. |
| `transaction_reference` | VARCHAR| UNIQUE, NULLABLE | Reference ID provided by the external Payment Gateway (e.g., Stripe/PayPal ID). |
| `idempotency_key` | VARCHAR | UNIQUE | Key generated by the client to safely retry the payment request without double charging. |
| `amount` | DECIMAL | `> 0` | The exact monetary amount requested. |
| `provider` | VARCHAR | | E.g., 'STRIPE', 'PAYPAL'. |
| `status` | ENUM | | `PENDING`, `SUCCESS`, `FAILED`, `TIMEOUT`, `REFUNDED`. |
| `created_at` | TIMESTAMP| | When the payment request was initiated. |
| `updated_at` | TIMESTAMP| | When the payment status last changed. |

### Duplicate Payment Prevention
1. **Idempotency Key (Database Unique Constraint)**: The API Gateway/Payment Service demands an `Idempotency-Key` header. This is saved in the database with a UNIQUE constraint. If a duplicate request arrives, the DB rejects the insert, and the API returns the cached response of the initial request.
2. **Transaction Reference**: Once the external provider acknowledges the payment, their unique `transaction_reference` is saved. This ensures we can reconcile exact transactions and avoid duplicate processing of webhooks.

### Transaction Boundaries
- Creating a payment record happens *before* calling the external provider.
- Updating the payment status to `SUCCESS` and publishing a `PaymentSucceeded` event happen in an atomic transaction (using the Outbox pattern) to ensure we never lose the state transition if the Order Service goes down.
